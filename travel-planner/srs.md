## 1. Введение

### 1.1 Назначение

Настоящий документ описывает функциональные и нефункциональные требования к системе совместного планирования групповых поездок **TravelTech**. Документ предназначен для:

- **Разработчиков** — как источник требований к реализации;
- **Тестировщиков** — как основа для создания тест-кейсов;
- **Архитекторов** — как входные данные для проектирования системы;
- **Заказчиков** — как описание возможностей системы.

### 1.2 Область применения

Система TravelTech обеспечивает согласованное совместное планирование групповых поездок, где несколько участников параллельно редактируют план поездки.

**Ключевая задача:** обработка сценария, когда:
- один участник добавляет рейс;
- другой — отель;
- третий — активность;
- четвёртый редактирует или удаляет элемент.

**При этом:**
- участники могут быть в разных часовых поясах и работать офлайн;
- все изменения доступны всем участникам в реальном времени;
- при конфликтах система предлагает стратегии слияния (merge);
- поддерживаются предложенные варианты и текущее состояние плана.

**Особенности проектирования:**
- Многопользовательский режим для семейных и групповых поездок;
- Интеграции с внешними API с учётом российского контекста;
- Обработка платежей и документов;
- Работа с часовыми поясами и международными форматами;
- Персонализация без утечки персональных данных.

## 2. Общее описание

### 2.1 Перспективы системы

TravelTech решает проблему неэффективного совместного планирования групповых поездок, когда участники используют разные инструменты (мессенджеры, таблицы, заметки) и теряют синхронизацию.

**Текущая ситуация:**
- Планирование происходит в чатах, где информация теряется;
- Нет единого источника истины о плане поездки;
- Конфликты (например, два отеля на одни даты) решаются вручную;
- Оплата разрозненна, нет прозрачности расходов;
- Данные детей передаются небезопасно.

**Целевая ситуация:**
- Единая платформа для совместного планирования в реальном времени;
- Автоматическое разрешение конфликтов через голосование;
- Прозрачная оплата с разделением расходов;
- Безопасное хранение данных детей с шифрованием AES-256;
- Интеграция с российскими провайдерами для поиска и бронирования.

**Бизнес-ценность:**
- Сокращение времени планирования поездки на 60%;
- Устранение конфликтов между участниками;
- Повышение безопасности персональных данных;
- Упрощение процесса оплаты и бронирования.

### 2.2 Функции продукта

Система TravelTech предоставляет пользователям следующие возможности в выпуске 1.0:

- **Регистрация и управление профилем** — создание учётной записи, заполнение профиля (имя, email, часовой пояс), аутентификация через JWT;
- **Создание групповой поездки и приглашение участников** — организатор создаёт поездку и приглашает участников по email или ссылке;
- **Совместное планирование маршрута** — добавление рейсов, отелей и активностей в реальном времени с синхронизацией между участниками;
- **Поиск и бронирование предложений** — интеграция с российскими провайдерами:
  - Авиабилеты: СИРЕНА-Трэвел (основной), Яндекс.Авиа (резервный);
  - Отели: Ostrovok.ru (основной), Яндекс.Путешествия (резервный);
  - Активности: Sputnik8 (основной), Tripster (резервный);
- **Работа в офлайн-режиме** — локальное хранение изменений с автоматической синхронизацией при восстановлении соединения;
- **Автоматическое разрешение конфликтов** — голосование с учётом веса голосов (организатор имеет удвоенный вес);
- **Автоматизированная оплата** — оплата элементов поездки через ЮKassa (основной) или СБП (резервный) с финальным бронированием у провайдеров;
- **Учёт детей** — добавление детей с возрастными тарифами и защитой персональных данных (шифрование AES-256, удаление через 30 дней после поездки);
- **Push и email-уведомления** — информирование о ключевых событиях (приглашения, конфликты, статусы бронирований);
- **Персонализация без утечки данных** — локальное хранение предпочтений на устройстве, отправка обезличенных паттернов для агрегированных рекомендаций.

### 2.3 Классы пользователей

#### 2.3.1 Организатор (Organizer)

**Описание:** Пользователь, создавший поездку. Имеет расширенные права управления.

**Характеристики:**
- Создаёт и удаляет поездки;
- Приглашает и удаляет участников;
- Утверждает финальный план поездки;
- Имеет право вето при разрешении конфликтов;
- Видит полную стоимость поездки;
- Может добавлять детей любого участника.

**Частота использования:** Ежедневно в период планирования.

#### 2.3.2 Участник (Participant)

**Описание:** Пользователь, приглашённый в поездку организатором.

**Характеристики:**
- Предлагает элементы плана (рейсы, отели, активности);
- Голосует при разрешении конфликтов (вес голоса — 1);
- Редактирует только свои элементы;
- Может добавлять только своих детей;
- Видит общую стоимость и свою долю расходов.

**Частота использования:** Ежедневно в период планирования.

#### 2.3.3 Гость (Guest)

**Описание:** Незарегистрированный пользователь, получивший ссылку-приглашение.

**Характеристики:**
- Может просмотреть информацию о поездке;
- Должен зарегистрироваться для участия в планировании.

**Частота использования:** Однократно при получении приглашения.

### 2.4 Рабочая среда

#### 2.4.1 Клиентская часть

- **Веб-приложение:** современные браузеры (Chrome 90+, Firefox 88+, Safari 14+, Edge 90+);
- **Мобильное приложение:** iOS 14+ и Android 10+;
- **Разрешение экрана:** адаптивный дизайн от 320px (мобильные) до 2560px (десктоп).

#### 2.4.2 Серверная часть

- **Операционная система:** Linux (Ubuntu 22.04 LTS или аналог);
- **Контейнеризация:** Docker 20.10+, Kubernetes 1.25+;
- **Базы данных:** PostgreSQL 15+, Redis 7+;
- **Брокер сообщений:** Apache Kafka 3.4+;
- **Облачный провайдер:** Yandex Cloud или VK Cloud (с учётом требований 152-ФЗ).

#### 2.4.3 Внешние системы

- **Провайдеры поиска и бронирования:** СИРЕНА-Трэвел, Ostrovok.ru, Яндекс.Авиа, Яндекс.Путешествия, Sputnik8, Tripster;
- **Платёжные системы:** ЮKassa, СБП;
- **Сервисы уведомлений:** Firebase Cloud Messaging, SMTP-сервер.

### 2.5 Ограничения

#### 2.5.1 Технические ограничения

- **Максимальное количество участников в поездке:** 20 человек (ограничение производительности синхронизации);
- **Максимальное количество одновременных редакторов:** 20 человек (FR-01.01);
- **Время хранения офлайн-данных:** 30 дней (NFR-04);
- **Время синхронизации изменений:** не более 5 секунд (NFR-01);
- **Время поиска через API провайдеров:** не более 10 секунд (NFR-02).

#### 2.5.2 Бизнес-ограничения

- **География:** система ориентирована на российский рынок (российские провайдеры, рубли, 152-ФЗ);
- **Языки:** русский и английский (NFR-13);
- **Валюты:** рубли (RUB) как основная, доллары (USD) и евро (EUR) для международных рейсов;
- **Модель монетизации:** комиссия с провайдеров (affiliate-модель) — не входит в scope MVP.

#### 2.5.3 Правовые ограничения

- **152-ФЗ:** хранение персональных данных граждан РФ на территории РФ;
- **GDPR:** применимо для пользователей из ЕС (если такие будут);
- **PCI DSS:** обработка платёжных данных через сертифицированные шлюзы (ЮKassa, СБП);
- **Срок исковой давности:** 3 года (ГК РФ, статья 196) — данные поездок хранятся не менее 3 лет.

### 2.6 Допущения и зависимости

#### 2.6.1 Допущения

1. **Стабильность внешних API:** провайдеры (СИРЕНА, Ostrovok и др.) обеспечивают доступность API на уровне 99% и выше;
2. **Доступность платёжных шлюзов:** ЮKassa и СБП работают без длительных перебоев;
3. **Корректность данных провайдеров:** провайдеры возвращают актуальные данные о рейсах, отелях и активностях;
4. **Надёжность интернет-соединения:** у большинства пользователей есть стабильный доступ к интернету (офлайн-режим — исключение, а не правило);
5. **Компетентность пользователей:** пользователи базово владеют веб- и мобильными приложениями.

#### 2.6.2 Зависимости

1. **Внешние API провайдеров:** система зависит от доступности и стабильности API СИРЕНА, Ostrovok, Яндекс.Авиа, Яндекс.Путешествия, Sputnik8, Tripster;
2. **Платёжные шлюзы:** система зависит от ЮKassa и СБП для проведения платежей;
3. **Сервисы уведомлений:** система зависит от Firebase Cloud Messaging и SMTP-сервера для доставки уведомлений;
4. **Инфраструктура:** система зависит от облачного провайдера (Yandex Cloud / VK Cloud) для размещения сервисов;
5. **Open-source компоненты:** система использует PostgreSQL, Redis, Kafka, Spring Boot, FastAPI, Node.js — зависит от их поддержки и обновлений.

## 3. Функциональные требования

### 3.1 Управление пользователями

#### FR-01.01 Регистрация
**Описание:** Пользователь может создать учётную запись, указав email, пароль и имя.  
**Приоритет:** Высокий  
**Источник:** User Service

#### FR-01.02 Аутентификация
**Описание:** Пользователь может войти в систему по email и паролю. Система выдаёт JWT-токен.  
**Приоритет:** Высокий  
**Источник:** User Service

#### FR-01.03 Управление профилем
**Описание:** Пользователь может редактировать имя, email, часовой пояс.  
**Приоритет:** Средний  
**Источник:** User Service

#### FR-01.04 Подтверждение email
**Описание:** Система отправляет письмо с ссылкой для подтверждения email.  
**Приоритет:** Средний  
**Источник:** User Service, Notification Service

### 3.2 Управление поездками

## 5. Модель данных

### 5.1 Основные сущности

#### User (Пользователь)
- `id` (UUID, PK)
- `email` (VARCHAR, UNIQUE, NOT NULL)
- `password_hash` (VARCHAR, NOT NULL)
- `full_name` (VARCHAR, NOT NULL)
- `timezone` (VARCHAR, DEFAULT 'Europe/Moscow')
- `email_verified` (BOOLEAN, DEFAULT FALSE)
- `created_at` (TIMESTAMP)
- `updated_at` (TIMESTAMP)

#### Trip (Поездка)
- `id` (UUID, PK)
- `title` (VARCHAR, NOT NULL)
- `description` (TEXT)
- `destination` (VARCHAR)
- `start_date` (DATE)
- `end_date` (DATE)
- `status` (ENUM: draft, planning, confirmed, booking, booked, active, completed, cancelled)
- `created_by` (UUID, FK → User)
- `created_at` (TIMESTAMP)
- `updated_at` (TIMESTAMP)

#### TripParticipant (Участник поездки)
- `id` (UUID, PK)
- `trip_id` (UUID, FK → Trip)
- `user_id` (UUID, FK → User)
- `role` (ENUM: organizer, participant)
- `joined_at` (TIMESTAMP)

- `id` (UUID, PK)
- `trip_participant_id` (UUID, FK → TripParticipant)

- `birth_date` (DATE, NOT NULL)
- `age_group` (ENUM: infant_0_2, child_3_12, teen_13_17)
- `document_data` (TEXT, ENCRYPTED AES-256)
- `created_at` (TIMESTAMP)

#### FlightBooking (Бронирование рейса)
- `id` (UUID, PK)
- `trip_id` (UUID, FK → Trip)
- `created_by` (UUID, FK → TripParticipant)
- `provider` (VARCHAR: sirena, yandex_avia)
- `external_booking_id` (VARCHAR)
- `status` (ENUM: proposed, voting, approved, booked, cancelled, conflict)
- `flight_number` (VARCHAR)
- `airline` (VARCHAR)
- `departure_airport` (VARCHAR)
- `arrival_airport` (VARCHAR)
- `departure_datetime` (TIMESTAMP)
- `arrival_datetime` (TIMESTAMP)
- `cabin_class` (VARCHAR)
- `price` (DECIMAL)
- `currency` (VARCHAR: RUB, USD, EUR)
- `created_at` (TIMESTAMP)
- `updated_at` (TIMESTAMP)

#### HotelBooking (Бронирование отеля)
- `id` (UUID, PK)
- `trip_id` (UUID, FK → Trip)
- `created_by` (UUID, FK → TripParticipant)
- `provider` (VARCHAR: ostrovok, yandex_travel)
- `external_booking_id` (VARCHAR)
- `status` (ENUM: proposed, voting, approved, booked, cancelled, conflict)
- `hotel_name` (VARCHAR)
- `address` (VARCHAR)
- `check_in_date` (DATE)
- `check_out_date` (DATE)
- `room_type` (VARCHAR)
- `price` (DECIMAL)
- `currency` (VARCHAR: RUB, USD, EUR)
- `created_at` (TIMESTAMP)
- `updated_at` (TIMESTAMP)

#### ActivityBooking (Бронирование активности)
- `id` (UUID, PK)
- `trip_id` (UUID, FK → Trip)
- `created_by` (UUID, FK → TripParticipant)
- `provider` (VARCHAR: sputnik8, tripster)
- `external_booking_id` (VARCHAR)
- `status` (ENUM: proposed, voting, approved, booked, cancelled, conflict)
- `activity_name` (VARCHAR)
- `location` (VARCHAR)
- `activity_datetime` (TIMESTAMP)
- `duration_hours` (DECIMAL)
- `price` (DECIMAL)
- `currency` (VARCHAR: RUB, USD, EUR)
- `created_at` (TIMESTAMP)
- `updated_at` (TIMESTAMP)

#### FlightBookingParticipant (Связь рейса с участниками)
- `id` (UUID, PK)
- `flight_booking_id` (UUID, FK → FlightBooking)

#### HotelBookingParticipant (Связь отеля с участниками)
- `id` (UUID, PK)
- `hotel_booking_id` (UUID, FK → HotelBooking)
- `trip_participant_id` (UUID, FK → TripParticipant)

#### ActivityBookingParticipant (Связь активности с участниками)

- Уникальность: (activity_booking_id, trip_participant_id)

- `child_id` (UUID, FK → ChildPassenger)
- `flight_booking_id` (UUID, FK → FlightBooking)
- Уникальность: (child_id, flight_booking_id)

#### ChildBookingHotel (Связь ребёнка с отелем)
- `id` (UUID, PK)
- `child_id` (UUID, FK → ChildPassenger)
- `hotel_booking_id` (UUID, FK → HotelBooking)

- `provider` (VARCHAR: yookassa, sbp)
- `external_payment_id` (VARCHAR)

- `created_at` (TIMESTAMP)
- `updated_at` (TIMESTAMP)

### 5.2 Статусы

#### Статусы поездки (trip_status)
- `draft` — черновик;
- `planning` — планирование;
- `confirmed` — утверждена;
- `booking` — идёт бронирование;
- `booked` — всё забронировано;
- `active` — поездка идёт;
- `completed` — завершена;
- `cancelled` — отменена.

#### Статусы бронирования (booking_status)
- `proposed` — предложен;
- `approved` — утверждён;
- `booked` — забронирован;
- `cancelled` — отменён;
- `payment_failed` — ошибка оплаты;
- `conflict` — конфликт.

#### Роли участников (participant_role)
- `organizer` — организатор;
- `participant` — участник.

#### Возрастные группы детей (age_group)
- `infant_0_2` — младенец (0-2 года);
- `child_3_12` — ребёнок (3-12 лет);
- `teen_13_17` — подросток (13-17 лет).

### 6.2 Fallback-стратегии

1. Запрос к СИРЕНА-Трэвел;
2. При ошибке или отсутствии данных — запрос к Яндекс.Авиа;
3. При ошибке обоих провайдеров — ручной ввод данных пользователем.

#### 6.2.2 Поиск отелей
1. Запрос к Ostrovok.ru;
2. При ошибке или отсутствии данных — запрос к Яндекс.Путешествия;
3. При ошибке обоих провайдеров — ручной ввод данных пользователем.

#### 6.2.3 Поиск активностей
1. Запрос к Sputnik8;
2. При ошибке или отсутствии данных — запрос к Tripster;
3. При ошибке обоих провайдеров — ручной ввод данных пользователем.

#### 6.2.4 Платежи
1. Запрос к ЮKassa;
2. При ошибке — запрос к СБП;
3. При ошибке обоих шлюзов — уведомление пользователя и повторная попытка.

#### 6.2.5 Уведомления
1. Отправка push-уведомления через Firebase;
2. При ошибке — отправка email через SMTP;
3. При ошибке обоих каналов — запись в лог и повторная попытка через 5 минут.

## 7. Архитектура системы

### 7.1 Микросервисы

| Сервис | Технология | Ответственность |
|--------|------------|-----------------|
| **API Gateway** | Node.js + Express | Маршрутизация запросов, аутентификация, rate limiting |
| **User Service** | Java + Spring Boot | Управление пользователями, профили, аутентификация |
| **Trip Service** | Java + Spring Boot | Управление поездками, участниками, бронированиями, синхронизация |
| **Search Service** | Python + FastAPI | Поиск рейсов, отелей, активностей через внешние API, кеширование |
| **Payment Service** | Java + Spring Boot | Обработка платежей, интеграция с платёжными шлюзами |
| **Conflict Service** | Python + FastAPI | Разрешение конфликтов, голосование |
| **Notification Service** | Node.js + Express | Отправка push и email уведомлений |

### 7.2 Взаимодействие сервисов

#### Синхронное взаимодействие (REST)
- API Gateway → все сервисы;
- Trip Service → User Service (получение данных пользователя);
- Trip Service → Search Service (получение деталей рейсов/отелей);
- Trip Service → внешние API (бронирование у провайдеров);
- Payment Service → ЮKassa/СБП (проведение платежей);
- Search Service → внешние API (поиск);
- Notification Service → Firebase/SMTP (отправка уведомлений).

#### Асинхронное взаимодействие (Kafka)
Асинхронное взаимодействие (Kafka)

**User Service публикует:** `UserCreated`, `UserUpdated`, `UserDeleted`

**Trip Service публикует:**
- Управление поездками: `TripCreated`, `TripUpdated`, `TripDeleted`
- Управление участниками: `ParticipantAdded`, `ParticipantRemoved`
- Управление рейсами: `FlightAdded`, `FlightUpdated`, `FlightRemoved`
- Управление отелями: `HotelAdded`, `HotelUpdated`, `HotelRemoved`
- Управление активностями: `ActivityAdded`, `ActivityUpdated`, `ActivityRemoved`
- Управление детьми: `ChildAdded`, `ChildRemoved`, `ChildLinked`
- Статусы бронирований: `BookingStatusChanged`

**Payment Service публикует:** `PaymentSucceeded`, `PaymentFailed`

**Conflict Service публикует:** `ConflictDetected`, `ConflictResolved`

**Trip Service потребляет:** `UserUpdated`, `PaymentSucceeded`, `PaymentFailed`, `ConflictResolved`

**Conflict Service потребляет:** все события Trip Service

**Notification Service потребляет:** все события от всех сервисов

#### Хранение данных
- **PostgreSQL** — реляционные данные (Database per Service);
- **Redis** — кеширование результатов поиска и платёжных сессий;
- **Kafka** — брокер сообщений для асинхронных событий.

## 8. API спецификация

Полная спецификация REST API доступна в отдельном документе:

- **Trip Service**: [OpenAPI спецификация](/trip_service/api/openapi.yaml) (OpenAPI 3.0.1)

### 8.1 Ключевые группы эндпоинтов

Все эндпоинты имеют префикс `/api/v1`.

**Управление поездками:**
- `POST /trips` — создать поездку
- `GET /trips/{id}` — получить поездку
- `PUT /trips/{id}` — обновить поездку
- `POST /trips/{id}/participants` — пригласить участника

**Синхронизация изменений:**
- `POST /trips/{id}/sync` — синхронизировать изменения
- `GET /trips/{id}/changes?since={timestamp}` — получить изменения

**Управление элементами:**
- `POST /trips/{id}/flights` — добавить рейс
- `POST /trips/{id}/hotels` — добавить отель
- `POST /trips/{id}/activities` — добавить активность
- `PUT /bookings/{type}/{id}` — редактировать элемент
- `DELETE /bookings/{type}/{id}` — удалить элемент

**Конфликты и голосование:**
- `GET /trips/{id}/conflicts` — список конфликтов
- `POST /conflicts/{id}/resolve` — разрешить конфликт
- `POST /conflicts/{id}/vote` — проголосовать

**Дети в поездке:**
- `POST /trips/{id}/children` — добавить ребёнка
- `DELETE /children/{id}` — удалить ребёнка
- `POST /children/{id}/link` — привязать к бронированию

**Интеграции с провайдерами:**
- `GET /providers/flights/search` — поиск рейсов
- `GET /providers/hotels/search` — поиск отелей
- `GET /providers/activities/search` — поиск активностей

**Платежи:**
- `POST /payments` — создать платёж
- `GET /payments/{id}` — получить статус платежа

### 8.2 Примеры запросов

Примеры запросов и ответов приведены в OpenAPI спецификации Trip Service (раздел "Examples").
